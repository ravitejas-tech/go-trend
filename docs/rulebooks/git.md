# Git Rules

Governs branches, commits, and history. Read before committing.

## Approval (non-negotiable)

**Never commit or push without explicit approval for that specific batch.** Approval is per-batch and never carries forward — being told "commit and push" once does not authorise the next set.

Finish the work, verify it, leave it in the working tree, and report what is ready. Staging with `git add` so a diff can be reviewed is fine; creating a commit is not.

Applies to AI agents and humans alike.

## One file, one commit

**Every commit touches exactly one file.** No bundling a module with its test, no sweeping a rename in one go.

- A commit touching two files becomes two commits, each with its own message.
- If a change genuinely cannot be split — a rename git tracks as one operation, a lockfile regenerated by a manifest edit — say so in the commit body. That is the only escape.
- Order the sequence so the tree is as coherent as possible at each step: introduce a module before the code importing it, land a test after the behaviour it covers, add a migration before the repository that queries the column.

**A mechanical change spanning many files may be batched** — a folder restructure, a scaffolded Next.js app, or one config addition repeated across the project. Splitting those per file produces noise, not history: every commit would carry the same message. Feature work is not mechanical and stays one file per commit. When in doubt, ask.

The cost is more commits and intermediate states that may not individually build. What it buys is `git log -- <path>` being a complete, honest account of one file, and a bisect landing on one file rather than a batch.

**The final commit of a sequence must build and pass checks.** Never push a sequence whose tip is broken — on Vercel, the tip of a branch is a deployment.

## Commit messages

Conventional Commits:

```
<type>(<scope>): <subject>

<body>

<footers>
```

**Types:** `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. No others.

**Scopes:** the area touched — `templates`, `generation`, `upload`, `admin`, `auth`, `db`, `ui`, `docs`. Keep the set small and reuse existing ones rather than inventing a scope per change.

**Subject:** imperative mood ("add", not "added"), lowercase after the colon, no trailing period, under 72 chars. Name the change, not the file — `fix(generation): mark stale pending rows as failed on read`, never `fix(generation): update route.ts`. The file is already in the diff.

**Body:** required whenever the subject is not self-evident. Explain _why_: the problem and how it surfaced, why this approach over the obvious alternative, what was deliberately not done, what was verified. Wrap at 72 chars. Prose, not a bullet list of the diff.

Per the no-comments rule, reasoning that cannot live in code lives here.

**Footers:**

| Footer                    | Meaning                                                |
| ------------------------- | ------------------------------------------------------ |
| `Refs #N`                 | Related to the issue. The only issue footer used here. |
| `BREAKING CHANGE: <what>` | Incompatible change, with migration path               |

**No `Co-Authored-By` trailer, and no AI attribution of any kind** — not in a commit, a PR description, or an issue comment. The commit author is whoever ran the work; how the diff was produced is not part of the history.

**Never write `Closes #N`, `Fixes #N` or `Resolves #N`** — in a commit, a PR description, or an issue comment. Those keywords auto-close the issue the moment the PR merges, and closing is QA's call after manual testing on the merged branch. An auto-close drops the issue out of their queue before anyone has verified the behaviour.

Use `Refs #N` and say in the body what was done and what remains. When work merges, comment on the issue naming the PR and say it is ready for QA — then leave it open.

## Branches

- `main` is the default branch and is protected — PR required, no force-push. It is what deploys to production.
- Names: `<type>/<short-slug>`, e.g. `feat/template-gallery`. With an issue: `feat/9-template-gallery`.
- Branch from `main`. Rebase onto `main` rather than merging it in, so history stays linear.
- Every branch gets a Vercel preview deployment. Verify the preview before requesting review — "works locally" is not a review-ready claim for a change to a route handler or an upload path.

## History is append-only once pushed

- **Never force-push a shared branch.** Correct a mistake with a new commit or a `revert`.
- Rebasing and squashing are fine on a **local, unpushed** branch, and expected before opening a PR.
- Never rewrite `main`.

## Never commit

- Credentials or tokens of any kind, and no `.env` file. `.env.local` is gitignored. The Gemini API key, Turso auth token, Blob token, and Auth.js secret live in Vercel's environment settings and nowhere in the repo.
- A `.env.example` may be committed, with empty values and no real keys.
- Generated artefacts — `.next/`, build output, caches, coverage.
- Uploaded or generated images, and test fixtures containing someone's photo.
- A second lockfile. This repo is Yarn 4 only; `npm install` produces a conflicting `package-lock.json`.
- Commented-out code. Delete it; git remembers.
